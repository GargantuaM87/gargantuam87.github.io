Currently, I'm building a x64-x86 Linux Debugger with an excellent book written by Sy Brand. It is an insightful book that is teaching me a lot about computer systems. As I continue with this project, I'm going to write a few logs to internalize the information I've learned and researched, and provide a more explicit direction for this project. 

These logs won't exactly be linear; I'm going to write about features and design patterns that I think are intriguing. In this case, this is about X-Macros.

If you're a new C developer or an experienced one, you've definitely heard about macros. They are pre-processor substitutes that can define constants and symbolic names whenever needed.

As this is a debugger project, I'm going to need to access our computer's CPU registers. Using X-Macros allows me to define a list of registers that I can reuse, and I can also generate statements from that list. This list allows statements and structures to be self-maintained; whatever we add or remove to this generated list will reflect in the statements and structures that source from the list. 

After I have my expanded register list from macro usage, I generate an ``enum`` and an ``array`` that takes from this list. We'll see those implementations in more detail later.

## X-Macros
Nested macros that can facilitate self-maintained and inter-dependent pieces of code. I'm going to post some examples of X-Macros that I have made, and do my best in explaining them thoroughly. 

Recently, this has been used to help me color terminal text through escape codes[^1]:
```c
namespace {
    enum Colors : uint8_t {
        BLACK = 30,
        RED = 31,
        GREEN = 32,
        YELLOW = 33,
        BLUE = 34,
        PURPLE = 35,
        CYAN = 36,
        WHITE = 37
    };

    // Converts a given text into another color or format based on the given color code.
    std::string ansi(std::string text, int color, int bold = 0) {
        std::string res = fmt::format("\e[{};{}m{}\e[0m", bold, color, text);
        return res;
    }
}

```

Cool enum, right? There isn't much wrong with it, but what if, for some baffling reason, I wanted to define and maintain this enum with macros? Let's see how that can be done...

```c
#define COLORS \
    X(BLACK, 30) \
    X(RED, 31) \
    X(GREEN, 32) \
    X(YELLOW, 33) \
    X(BLUE, 34) \
    X(PURPLE, 35) \
    X(CYAN, 36) \
    X(WHITE, 37)

// Utility Functions
namespace {
    enum Colors : uint8_t {
        #define X(value, a) value = (a),
            COLORS
        #undef X
    };
```

Here, we define a macro called `COLORS` and use our new line escape character to define multiple lines. On each line, there is a declaration for each element inside our list. These elements are a part of a macro (traditionally named 'X'), and the data within our list is defined with each subsequent argument. In this case, I want X to include the name of the color and its corresponding ANSI escape code.

Then, within an anonymous namespace, I define an enum called colors. We define an X-macro that sort of looks like it takes two parameters. I think it's alright to think of it in that way. Those parameters correspond to the position that we defined our values in the macro called `COLORS` above. This easily allows us to define each enum value in our enum block. Whatever we add or remove in the X-macro will reflect in the enum we have, making it self-maintained. 

The second part, within the enum, expands the list to generate statements. These statements are what set the enum names to their respective values. You can see that the expansion of the code above is exactly the same as what we had before:
```c
namespace {
    enum Colors : uint8_t {
        BLACK = 30,
        RED = 31,
        GREEN = 32,
        YELLOW = 33,
        BLUE = 34,
        PURPLE = 35,
        CYAN = 36,
        WHITE = 37
    };
}
```

You can imagine that these X-Macro expansions can be particularly useful for large datasets. Despite reducing code readability and not having a definite general use, when utilized in the right environment, they're quite powerful (especially for OS development).

## Registers
For this project, I have a file called [``registers.inc``](https://github.com/GargantuaM87/arc-debugger/blob/main/include/libadb/detail/registers.inc). Courtesy of Sy Brand and their wonderful design practices, by the way. This file is an "Include File", something that is used by other files to be included and executed. It doesn't run a program on its own. Later, you will see how this file is exactly used, but let's delve into the contents of this file:

Yeah... that's a lot. But with our explanation and examples of X-Macros earlier, hopefully this won't be too complicated to digest. At the top, we have a preprocessor statement that makes sure we use this file with the ``DEFINE_REGISTER`` macro. As we continue down, we encounter our first macro. ``GPR_OFFSET(reg) (offsetof(user, regs) + offsetof(user_regs_struct, reg))`` helps us define the byte offset of our given register. ``user``, ``regs``, and ``user_regs_struct`` are from the [``sys/user.h``](https://sites.uclouvain.be/SystInfo/usr/include/sys/user.h.html) header; you can research it yourself, but just know that they define most of the general-purpose and floating-point CPU registers that we can use. 

The ``DEFINE_GPR_64`` macro will take in a name for a register and its DWARF ID[^2]. Then we use nested macros, calling ``DEFINE_REGISTER`` with the following arguments: a name, DWARF ID, size in bytes, offset in bytes, register type, and format. The remaining macros of similar names define general-purpose subregisters[^3] of differing byte sizes.

The next list of macros defines floating-point register offsets, sizes, and the registers themselves. Then, after that, there are definitions for ``st``[^4], ``mm``[^5], and ``xmm``[^6] registers. 

The last macro definitions are responsible for debug registers, a very important part of our register list that allows us to enable hardware breakpoints (more on that in a later blog). 

### Implementation
```c 
// An ID type that represents an enumeration of a defined register.
    enum class register_id { 
	    #define DEFINE_REGISTER(name,dwarf_id,size,offset,type,format) name
        #include "./detail/registers.inc"
        #undef DEFINE_REGISTER
    };
```

In one of the examples above, we defined an enum with X-macros. In this case, we're doing the same thing. Using the X-Macro ``DEFINE_REGISTER``, we can define each enum value inside register_id by including ``registers.inc``. Note that each enum value corresponds to the name elements of each definition, so ``register_id`` would consecutively be: ``rax``, ``rdx``, ``rcx``, ``rsi``, ...basically listing all of the CPU registers (general-purpose, floating-point, and debug). 

```c
// Information for a register.
    struct register_info {
        register_id id;
        std::string_view name;
        std::int32_t dwarf_id;
        std::size_t size;
        std::size_t offset;
        register_type type;
        register_format format;
    };
```

```c 
inline constexpr const register_info g_register_infos[] = {
        #define DEFINE_REGISTER(name,dwarf_id,size,offset,type,format) \
	        { register_id::name, #name, dwarf_id, size, offset, type, format }
        #include "./detail/registers.inc"
        #undef DEFINE_REGISTER
    };
```

A little different. We're filling in an array of ``register_info``, providing the necessary information, and, as before, including ``registers.inc`` to make sure we get all our register definitions. I don't access this array directly when using it; instead, I use iterator functions to return a reference to a register that I want to find, whether through its ID, name, or DWARF ID.

As you can see, X-Macros have been extremely useful for creating our enum ``register_id`` and array ``register_info``. I imagine that if I hadn't used X-Macros, I would have had to write a wicked amount of code inside my header file.

[^1]:ANSI *(American National Standards Institute)* escape codes. The list for ANSI color codes can be found [here](https://gist.github.com/JBlond/2fea43a3049b38287e5e9cefc87b2124).
[^2]:A DWARF *(Debug With Arbitrary Record Format)* ID is an integer that is mapped to each register. The mapping is dependent on your CPU architecture's ABI *(Application Binary Interface)*.
[^3]: Subregisters are just specific regions of its super register. In this case, look at the register ``rax`` register which is known as the accumulator register. We define it with its name and DWARF ID of 0. Then further down, ``DEFINE_GPR_32(eax, rax)`` represents the lower 32-bits (4 bytes) of ``rax``. ``DEFINE_GPR_16(ax, rax)`` is the lower 16-bits of of ``eax``. Finally, we define both ``ah`` and ``al``, which represents the higher and lower 8-bits of the ``ax`` register respectfully. Writing to ``ax`` will modify both ``ah`` and ``al``, and modifying ``ah`` or ``al`` will modify ``ax``. You can imagine that it's similar for the other subregisters. 
[^4]: ``st`` registers number from ``st0`` to ``st7``. These are known as ``x87`` registers and they operate in a push/pop fashion relative to ``st0`` at the top of the stack. All eight of these registers are 80-bits and they are succeeded by more modern instructions, yet still used due to ``x87`` compatibility.
[^5]: ``mmx`` uses eight 64-bit registers, named ``mm0`` through ``mm7``. These extended upon ``x86`` instructions, which allowed for operation on multiple pieces of data simultaneously, which is called SIMD *(Single Instruction Multiple Data)* instructions. These set of registers cannot be used at the same time with ``x87`` floating point registers as they map to the same memory locations.
[^6]:``xmm`` registers were introduced by SSE *(Streaming SIMD Extensions)* instructions, which succeeded ``x87`` instructions. This set of registers include eight 128-bit registers named ``xmm0`` through ``xmm7``. SSE was expanded multiple times: SSE2, which doubled the set of registers to 16 128-bit registers, SSE3 in 2004, and SSE4 in 2006.
